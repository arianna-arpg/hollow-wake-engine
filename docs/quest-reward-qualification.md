# Durable final-vocation rewards

This internal integration joins trusted final-vocation turn-ins to the character
and account save owner. It is not an exported complete-character API or a native
engine addon. Package checks exclude all 43 internal character modules, including
the twelve introduced here. Public exports and runtime dependencies are unchanged.
The source boundary checks every public subpath and its type dependencies, so an
export cannot depend on an omitted internal file. Its controls also remove their
temporary source copies on success and failure.

## Transaction and host boundary

The host supplies trusted quest eligibility, content identity, reward rules and
storage. The owner rejects an already-completed quest before authorization, minting
or storage. A successful turn-in commits XP, passive/vocation points, vocation,
run/account stamps, quest book, pending Memory rewards and the owned random stream
in one compare-and-swap checkpoint. Reads retain their old state until the storage
acknowledgement. Concurrent writers must reconcile; a lost acknowledgement is
resolved by reopening durable state rather than paying again.

Checkpoint schema 2 identifies the diagnostic minted-vocation capability. Admission
requires each completed quest to have a positive safe run stamp, and each active
quest to have no completion stamp. Full run-ledger capacity refuses the entire
preparation, including XP milestones and completion stamps. Even when private
minting ran first, refusal does not advance the saved stream or publish effects.

Prepared rewards contain no recipient item identifiers. Pickup assigns those
identifiers under the receiving character's ownership. Publication consumes a
one-use lease before callbacks; partially failed publication requires recovery.
Transient labels and geometry are not additional durable reward obligations.

## Content and runtime cost

The final-reward compiler projects 31 final payouts from the accepted vocation
survey. The existing vocation compiler retains all 92 authored chain steps and
their gates. No accepted fixture is regenerated by these tests.

The Memory catalogue projects 948 skill rows and 457 support rows from accepted
pouch data, preserving registry order. It validates and detaches those rows once
at load. Captured host rules then prepare the draw schedule for Memory-only
rewards. Repeated rolls read no authored definitions and return a shared frozen
sentinel without allocating the gem that the original Memory path discards.
The tests retain empty pools, starter fallback, zero weights, floating-point
multiplication order and random draw counts. Negative/nonfinite weights and
overflowing totals are rejected. This policy is not a bare-gem selector.

Content identities detect mismatched data; they do not authenticate host-supplied
rules. Gameplay has no database runtime dependency. SQLite is the test storage
backend for atomic checkpoint and fresh-process recovery, not a query inside
each reward roll. No timing, allocation-profiler or target-device claim follows
from these structural changes.

## Reproduction

Build first. Normal commands read maintained sources and pinned original inputs,
record their hashes and compressed logs, and clean their owned work directories
even when a course fails. The declarations retain 38 deliberate faults across
nine behavior courses. The two type courses are separate.

| Command | Required coverage |
| --- | --- |
| `npm run test:quest-reward-types` | SDK graph, 60 existing rejected calls plus 70 quest-path rejected calls |
| `npm run test:quest-rewards` | Mint: 13 contracts/3 faults; rolls: 45 cases/7 faults; catalogue: 21 cases/3 faults; publication: 12 contracts/4 faults; ownership: 35 cases/9 faults; capacity rollback: 2 cases/2 faults; SQLite: four fresh operating-system processes |
| `npm run reference:quest-rewards` | Original production types; 45 original roll cases/5 faults; 37 live World cases across 31 vocations/5 faults |

Normal and restored controls surround the faults. SQLite phases cover a lost
acknowledgement, pickup with fresh handles, a subsequent quest continuing the
saved stream and final inspection without repayment. Two additional World seeds
exercise skill rewards as well as supports. The content-backed World fixture
also compares every projected row with the original registries.

The original/control World arms each use a separate owned reward stream. The
comparison includes the original label-jitter draw and visible callback order;
it does not preserve historical interleaving with the game's global random
stream. The World fixture writes prepared labels directly, and does not claim
compatibility with private interception of World.text.

The shared character-build test helper compiles original skill and minion
definitions into each course. These source-based courses do not replace the
separate [installed character-build factory checks](character-builds.md).
General quest acceptance, choices, cargo/postings,
repeatable quests, Odyssey progression, whole-World saves, combat randomness,
installed native packages, physical power-loss recovery and Steam Deck/older
mobile measurements remain separate work.
